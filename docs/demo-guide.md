# 실제 지갑 시연 순서

로컬은 http://127.0.0.1:3000 입니다. [공개 웹](https://updish-hackathon-20261025-betaplayers-projects.vercel.app)은 최종 앱 코드를 배포했고 임시 테스트 지갑의 서명 로그인·개인 화면·로그아웃 검사를 통과했습니다. 이제 MetaMask가 설치된 브라우저에서 아래 순서로 실제 사용자 지갑을 확인합니다.

## 준비

- 운영/투자 지갑: `0x26473024a9118E8F39b1A0ce01AC726C36Dd0976`. 기존 GIWA 테스트 ETH를 배포·mint·기록 가스에 사용합니다.
- 두 번째 MetaMask 계정: 검토자. 로그인·검토만 하면 ETH가 필요하지 않습니다.
- [공식 Playground](https://sepolia-playground.giwa.io/)에서 운영 지갑으로 **Issue Dojang** 승인. ETH faucet과 별개이며 TESTNET FAUCET 발급자입니다. 앱에서 safe 반영 후 유효/UID를 확인합니다.
- 복구 구문·개인 키는 채팅/서버에 넣지 않습니다.

## 정상 흐름

1. 운영 지갑 로그인 → 검토/운영 → 두 번째 지갑에 REVIEWER 역할 지정.
2. 가게 운영자 워크스페이스 → 정상 CSV → 제출. 3,100만원−60만원−40만원=3,000만원과 중복 2건 확인.
3. 검토 지갑으로 로그인 → 가게 운영자 워크스페이스 → 사유 입력 → 검토·마감.
4. 운영 지갑 → 가상 배경 3,500단위 적재 → 투자 상품 표의 **청약 신청하기**로 상세 화면 진입 → 3개 이해 항목 확인 → 100단위 모의 청약. 아직 보유는 0.
5. 운영 → 전체 배정 확정. DB 보유 100, GIWA 대기. 배경은 체인 미발행.
6. GIWA 패널 → 토큰/정산 기록 계약 각각 지갑 배포 → 서버 검증·등록 → MINT 제출 → 영수증/safe 대조 → GIWA 100 확인.
7. 검토 지갑 → 마감 증빙으로 정산 산정. 운영 지갑 → 별도 승인. 전체 의무 900,000원, 개인 세전 25,000원.
8. SETTLEMENT 거래 제출 → safe/Explorer 확인. 원본 digest 일치·변조 후보 불일치 확인.
9. 모의 지급 성공/부분/실패와 미지급 잔액 확인. 실제 현금이나 테스트 자산 분배 성공이 아님.
10. 키 연결 후 본인 정산 Agent 설명 요청. 미연결이면 설명만 실패하고 업무는 계속됨. Bojagi는 공식 미연결.

거래 응답이 지연되면 다시 제출하기 전에 영수증/해시 복구를 사용합니다. 브라우저에는 공개 해시·주소만 저장합니다.

## 예외

- 부분 배정: 새 run → 배경 3,500 → 120 청약 → 사용자 100 배정·20단위/200,000원 모의 환불.
- 미달: 새 run → 100 청약 → 미달 환불. 보유 없음.
- 누락: 은행 누락 CSV는 보완 필요, 마감 불가.
- 현금 부족: 11월 CSV → 별도 마감/산정/승인. 의무 720,000원·현금 300,000원·부족 420,000원. 초과 지급 차단.
- 정정: 10월 정정 CSV → 별도 마감/산정/승인. 원본/차액/기지급 보존, 과거 버전 추가 지급 차단.
- 철회: Playground Revoke → safe 반영. 신규 참여 차단·기존 보유/명세 유지. false만으로 철회/만료 사유를 단정하지 않음.
- 만기: 미래 새 월 정산 차단·기존 청구 보존.
- 리셋: 과거 거래는 취소되지 않음. 새 상품 token ID에 맞는 새 토큰 계약이 필요함.

업무 금액은 SIMULATION이며, 지갑 승인 이후의 계약 배포·mint·digest만 실제 GIWA 테스트 거래입니다.


## 2026-10-26 화면과 시연 순서

1. **지갑 로그인 → 지갑 선택하고 연결**에서 MetaMask 등 설치된 지갑을 고릅니다. GIWA Sepolia로 전환하고 **서명하고 로그인**합니다. 연결만으로 서버 로그인되는 것은 아닙니다.
2. 상단 **운영자 모드**를 클릭해 가게·고객·투자자 화면을 바꾸며 설명할 수 있습니다. 화면 전환은 실제 계정/권한 변경이 아닙니다. 검토·승인 분리 시연은 여전히 두 번째 지갑으로 서명 로그인해야 합니다.
3. **청약 → 매출 차트**는 최신 승인 월 매출/전체 배분금, 로그인 후 내 정산액을 표시합니다. 처음에는 승인 자료가 없어 비어 있을 수 있습니다. **매출관리**에서 샘플 제출 → 다른 검토 지갑 마감/산정 → 운영 지갑 승인 후 차트에 표시됩니다.
4. **투자내역 → 정산 근거 보기**는 모델 없이도 작동합니다. AI 설명은 별도 API 키가 필요합니다. 정정 전 지급 25,000원, 정정 의무액 24,167원은 초과 833원으로 표시하고 자동 회수하지 않습니다.
5. 고객 관점은 가게 공개 정보 안내이며 주문·결제는 제공하지 않습니다. 운영 지갑을 투자자 화면으로 전환해도 다른 투자자의 보유액을 만들어 표시하지 않습니다.

사용자 Dojang 발급은 safe에서 확인했습니다. Playground의 TEST 토큰/UP ID 발급은 현재 서비스 참여의 필수 조건이 아닙니다. 최근 발급 후 앱에서 미확인이면 safe 반영을 기다리며 중복 발급하지 않습니다.

### 개발용 격리 리허설

`./scripts/rehearsal.ps1 -Action Start`는 별도 DB와 로컬 Anvil/Core 8081/Web 3001을 생성합니다. `pnpm smoke:business`는 Anvil임을 검사한 뒤 8건 동시 청약과 업무 전체 흐름을 확인합니다. `scripts/browser-role-flow.js`와 `scripts/browser-wallet-chart-flow.js`는 Playwright CLI의 `run-code --filename`용 함수입니다. 전자는 업무 E2E 후 v1 상태, 후자는 전자가 만든 v2 상태와 같은 테스트 브라우저를 사용합니다. 모의 provider는 origin 3001만 대상으로 하며 앱 소스에 포함되지 않습니다. `-Action Stop`은 소유 프로세스만 종료하고 DB를 보존합니다. 기존 로컬/클라우드 DB를 리셋하지 않습니다.


## 샘플 데이터로 바로 시연하기 (2026-10-26)

공개 화면은 승인된 정산 자료가 없을 때 2026-05~10 **샘플 CSV** 차트를 보여줍니다. 월 매출은 2,200/2,400/2,700/2,500/2,800/3,000만원입니다. 현재 3% 기준 전체 배분금 예시는 66/72/81/75/84/90만원입니다. 샘플을 실제 승인·개인 보유·지급으로 표시하지 않습니다. 승인 내역이 생기면 해당 기록을 우선 표시하며, 샘플/승인 버튼으로 전환할 수 있습니다.

1. 차트의 월별 **CSV 다운로드**, 또는 하단 **흐름 점검용 CSV 4종 내려받기**를 사용합니다.
2. 운영자/가게 담당자의 **매출관리 → 흐름 점검용 샘플 CSV**에서 정상/누락/현금 부족/정정을 클릭하면 대상 월과 제출 내용이 채워집니다. 월별 참고 자료도 선택할 수 있습니다.
3. **CSV 제출 · 서버 대조** 후 다른 검토 지갑으로 마감/산정하고, 산정자와 다른 지갑으로 승인합니다. 샘플 클릭 자체는 DB에 제출하거나 승인하지 않습니다.
4. 계약 전 5~9월은 참고용 매출이라 정산이 거절되는 것이 정상입니다. 정상 업무 정산은 계약 내 10월 자료부터 진행합니다. 은행 누락은 BLOCKED, 정정은 최초 10월 승인 후 진행합니다.

원본·기대 결과·생성/검증 명령은 [fixtures 안내](../fixtures/README.md)에 있습니다. 새 `browser-demo-guest.js`는 공개 샘플/차트/오류/다운로드 검사, `browser-demo-signed.js`는 `smoke:business` 직후의 별도 Anvil/DB에서 운영·검토 지갑으로 9개 CSV 제출과 정정 승인을 확인합니다. 사용자 지갑 거래를 보내지 않습니다.
