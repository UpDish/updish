# UpDish 발표 시연 순서 — v0.3

[DEMO 열기](https://updish-hackathon-20261025-betaplayers-projects.vercel.app/) · [발표 반영 기준](presentation-v03.md)

업비트 안에서 음식점 매출 연동 투자 서비스를 제공하는 상황을 제안하는 독립 DEMO다. 실제 업비트 계정·현금 투자와 연결되지 않는다. 브라우저 지갑은 연결과 로그인 서명을 하고, GIWA 거래 때만 테스트 ETH 가스비가 든다.

## 사전 준비

- 운영 지갑: 기존 운영 주소. 테스트 ETH가 필요하다. 설정된 운영 주소만 서버 OPERATOR 권한을 받는다.
- 투자 지갑: 운영 지갑과 다른 시연용 계정. 공식 GIWA Playground에서 TESTNET FAUCET Dojang을 발급한다. 보유 수량 발행까지 확인할 주소다.
- 검토 지갑: 운영·제출 지갑과 다른 계정. 운영자 계정 메뉴 → 검토·정산 콘솔 → 정산·분배 → 시연 준비 → 지갑 역할 설정에서 REVIEWER로 지정한다. 가게 담당자를 따로 둘 경우 MERCHANT로 지정한다.
- 계정 전환은 MetaMask에서 한 뒤 현재 지갑으로 다시 로그인한다. 화면의 관점 전환은 서버 권한이나 서명 지갑을 바꾸지 않는다.
- 계정 메뉴 → 검토·정산 콘솔 → 정산·분배 → 시연 준비에서 새 시연을 시작한다. 기존 실행과 과거 거래는 삭제되지 않는다. 가상 배경 9,900단위를 준비하면 투자 지갑의 100단위(100만원)로 1% 예시를 시연한다. 배경은 체인 미발행·분배 제외다.

## 발표 동선

1. ‘UpDish 열기’ → 표준 지갑 선택 → SIWE 서명 로그인. 첫 화면은 **가게 탐색**, 두 번째 탭은 **내 투자**다.
2. 성수 모퉁이 2호점 확장을 선택한다. 1억원 모집·2호점 개설 목적·전체 매출 배분율 10%·원금 별도 반환 없음·위험을 설명한다. 기간 60개월과 자금 사용 세부는 시연 가정이다.
3. 매출·대조에서 **본점 참고**와 **2호점 승인**을 구분한다. 본점 과거 실적을 미래 2호점 분배금으로 계산하지 않는다. POS·PG·은행 입금 대조 상세에서 누락·불일치를 보여줄 수 있다.
4. 청약하기 → 금액 입력 1,000,000원 → 조건 확인 100단위·1% → 위험 동의 → 모의 청약 신청. 내 투자 → 청약 내역에서 접수·보유 미반영을 확인한다. 배정 전에는 별도 확인창으로 취소할 수 있다.
5. 운영자는 계정 메뉴의 업무 콘솔 → 정산·분배 → 모집·배정에서 배정을 확정한다. DB 보유와 GIWA 발행 상태를 구분한다.
6. 제출 지갑은 가게 콘솔 → 매출 CSV 제출에서 **정상 · 중복 포함** 자료를 제출한다. 다른 검토 지갑은 자료 검토 → 대조 상세 → 사유 입력 → 마감, 이어서 정산을 산정한다. 은행 누락은 마감할 수 없다.
7. 산정자와 다른 운영 지갑이 정산·분배 → 해당 정산 관리에서 승인한다. 승인 매출 3,000만원 × 10% = 300만원, 100/10,000단위의 세전 의무액은 30,000원이다.
8. 정산·분배 → GIWA 기록 → 계약 설정에서 보유 수량 계약과 정산 기록 계약을 배포하고 검증·등록한다. 두 계약의 safe 확정을 기다리는 동안 **분배 계약 설정 → DEMO 토큰 배포**를 먼저 진행할 수 있다. 수량·기록 계약이 등록되면 분배 계약을 배포하고 검증·등록한다. 기존 배포는 확인·복구를 사용한다. 같은 상품 설정의 기존 주소를 입력할 수도 있다.
9. GIWA 기록에서 수량 발행·매출 확정 기록을 운영 지갑으로 제출하고 영수증·safe 반영을 확인한다. 가상 배경에는 mint를 요청하지 않는다. 응답이 지연되면 같은 거래를 재전송하지 않고 영수증을 확인한다.
10. 정산·분배 → 정산 관리에서 **DEMO 사용 승인·예치**를 누른다. 지갑에서 필요한 수량만 승인하고 예치한다. 예치 safe 확인 후 실제 투자 시연 지갑에 **지갑으로 DEMO 분배**를 실행한다. 테스트 ETH는 가스 자산, DEMO는 분배 테스트 자산으로 서로 다르다.
11. 투자 지갑 → 내 투자 → 분배 내역에서 **30,000 DEMO·수령 확인·거래 영수증**을 보여준다. 정산 산식·모의 원장은 접어서 구분한다. DEMO 수령과 모의 원화 지급을 합산하지 않는다.
12. Agent를 열어 가게의 공개 매출 대조나 본인의 승인 정산을 질문한다. 데스크톱은 IDE처럼 본문 옆 채팅, 모바일은 전체 화면 채팅이다. 모델은 거래를 실행하지 않는다.

## 예외 시연

실제 체인의 블록 포함과 safe 확정은 다르다. 2026-10-31 점검에서는 두 블록의 시각이 약 5분 30초 차이 났다. 초회 계약 준비·발행·예치를 발표 전에 마치고, 대기 중에는 같은 거래를 다시 보내지 않는다. 새 run은 새 상품 설정이므로 매번 초기화하면 계약 준비도 다시 필요하다. [전체 흐름 검사](full-flow-check-20261031.md)의 로컬 증거와 실제 지갑 이슈를 구분한다.

- 은행 자료 누락: 제출은 되지만 보완 필요 상태이며 마감·정산 근거 확정이 차단된다.
- 현금 부족: 11월 2,400만원 매출·240만원 의무 대비 현금 여력 30만원이다. 부족 사유가 해결되기 전 추가 예치를 막는다.
- 하향 정정: 최초 승인 후 정정 CSV를 제출해 다른 지갑 검토·승인을 거친다. 매출 2,900만원이면 의무액은 29,000원이다. 기존 30,000 DEMO 수령은 남고 추가 분배는 막힌다. 이전 버전 미확인 거래가 있으면 먼저 처리한다.
- Dojang 철회: 공식 Playground에서 사용자가 직접 서명한다. 이후 신규 참여는 막지만 기존 보유·명세·수령 기록은 지우지 않는다.

## 연결과 검증 범위

Vercel Web → EC2 Spring → 내부 FastAPI → 승인된 OpenAI 모델 연결이다. 키는 로컬 ignored 환경 파일과 EC2의 0600 환경 파일에만 보관한다. DB는 기존 EC2 PostgreSQL 18.6이며 Supabase는 사용하지 않는다. main 푸시는 Web 자동 배포를 트리거하고, EC2 이미지는 별도 검증·배포한다.

로컬 리허설은 `scripts/rehearsal.ps1`의 별도 DB·Anvil과 테스트 지갑을 쓴다. `pnpm smoke:presentation`은 실제 로컬 계약의 ERC-20 잔고 변화와 정정·중복 차단을 검증한다. `browser-integration-v03.js` → `browser-distribution-v03.js`는 별도 승인된 로컬 자동 검사다. 사용자의 실제 지갑과 GIWA 거래를 실행하지 않는다. 증거는 `docs/evidence/presentation-v03/`에 구분해 저장한다.

Bojagi는 공식 SDK·테스트 접근이 없어 NOT_CONNECTED다. Reown 공개 Project ID가 없어 모바일 QR 연결도 준비 중이다. 브라우저 지갑 선택·SIWE는 사용할 수 있다. 실제 GIWA 계약 배포·분배 최종 리허설은 위 순서대로 사용자 지갑 서명이 필요하다.
