# v0.2 대비 남은 개발 작업

점검일: 2026-10-25 KST. 기준: [해커톤 개발 스펙 v0.2](../../UpDish_해커톤_개발스펙_v0.2.md).

소스, DB migration, API 경로, 컨트랙트, 화면, 저장된 검증 결과를 대조했다. 이번 점검에서는 업무 코드를 변경하거나 클라우드를 생성하지 않았다.

## 현재 판정

프로젝트 기반·지갑 연결·SIWE·Dojang 조회가 구현됐다. 음식점 증빙 → 모의 청약·배정 → 보유 → 정산 → 테스트 분배 → Agent 설명의 업무 흐름과 클라우드 배포는 아직 구현 전이다. 현재 웹은 연동 확인용 단일 화면이며 완성된 투자 플랫폼 화면은 아니다.

전체 완성률을 임의의 백분율로 산정하지 않는다. 아래 완료 조건별로 구현과 검증을 구분한다.

## 완료와 실제 검증을 구분할 부분

- **로그인**: 실제 EIP-191 서명을 Java가 검증하고 PostgreSQL 세션을 만드는 로컬 HTTP 검증 기록이 있다. 브라우저 검증의 provider는 검증용으로 대체했다. 사용자 확장 지갑 조합의 최종 리허설은 남아 있다.
- **Dojang**: 실제 GIWA의 미인증 조회를 확인했다. 발급/유효 상태 해제 화면 전환은 모의 응답으로 검사했다. 사용자 지갑의 실제 발급·철회는 아직 실행하지 않았다.
- **Dojang 자격**: 현재는 조회만 한다. 청약 API와 mint가 없으므로 신규 참여 허용·차단이 구현됐다고 판정하지 않는다. 철회 후에도 기존 보유·명세·미지급 청구를 유지하는 규칙은 후속 업무에 적용해야 한다.
- **철회 사유**: 현재 false 응답만으로 미발급·철회·만료를 구분하지 않는다. 실제 철회 거래 영수증과 필요 조회를 연결하는 작업이 남아 있다.
- **GIWA**: 공식 계약 읽기만 연결됐다. UpDish의 토큰 mint·정산 digest 기록·분배 트랜잭션은 없다. Solidity helper 테스트는 토큰 발행 테스트가 아니다.
- **Agent**: 서버 기반이 있는 상태다. 모델 호출·근거 조회·설명 기능은 없다.
- **Bojagi**: 우리 저장소는 미연결이다. 기존 조사에서 공식 공개 SDK·테스트 호출 경로를 확인하지 못한 상태이며, 이번 점검은 신규 웹 조사나 접근 권한 확인을 수행한 것이 아니다. 공개 SDK가 없다고 단정하지 않는다.

## 권장 개발 순서

### 1. 가게·상품·역할·시연 데이터

- [ ] Store·Offering·ContractVersion과 준비된 테스트 계정/역할 migration.
- [ ] 가게·제출자·검토/승인자와 투자자 API 범위 정의. 다른 가게·타인 자료 접근 차단.
- [ ] 가게 1곳·상품 1개·정상 월 1개·오류/실패/만기 샘플을 고정.
- [ ] 상품 상세와 역할별 기본 화면, OpenAPI 타입 계약 연결.

이 단계에서 실제 화면에서 볼 상품과 계약을 만든다. 준비한 실제 지갑의 Dojang 발급·철회는 병행한다.

### 2. CSV 대조와 가게 검토

- [ ] 고정 CSV의 거래 연결·중복·할인·부분 환불·입금 차이·누락 검사.
- [ ] 자료 접수 → 보완/검토 → 마감, 원본 버전·담당자·시각·사유 보관.
- [ ] 샘플 증빙의 비공개 S3 업로드·완료 검증·권한 있는 다운로드.
- [ ] 3,000만원 정산대상 매출의 근거를 화면에서 확인.

### 3. Dojang 청약 → 배정 → GIWA 보유

- [ ] 서버 자격 검사 후 모의 청약. 모집 성공/미달·취소·부분 배정·환불 규칙.
- [ ] 배정과 DB 보유, mint 반영 상태를 구분하고 동시·중복 요청 방지.
- [ ] OpenZeppelin 버전 고정, UpDishDemoUnits 구현·권한·중복 배정 ID·이전 제한·Dojang 재검사.
- [ ] chain job·서명·제출·영수증 확인, 공식 테스트넷 배포와 Explorer 링크.
- [ ] 미인증 차단 → 발급 후 허용 → 실제 mint → 철회 후 신규 참여 차단 리허설.

### 4. 정산 → 정산 기록 → 모의 지급·정정

- [ ] 계약 버전·보유 기준·월 매출을 고정해 정수 원 단위로 계산. 금액 API는 십진 문자열.
- [ ] 개인별 절사 후 잔여 원을 결정적인 규칙으로 배분해 총액을 일치시킴.
- [ ] 분배 의무·현금 여력·실제 모의 지급 결과를 별도 보관. 세금·수수료 가정 표시.
- [ ] SettlementRegistry·salt·digest·비공개 원본·정정 참조 구현과 실제 GIWA 기록.
- [ ] 실패·부분 성공·중복 결과·잔여액 재시도·정정·만기. 만기 뒤 미지급 청구 보존.

### 5. Agent와 Bojagi

- [ ] 제한된 단일 Agent가 계약·대조 결과·개인 정산·증빙 발췌만 읽도록 연결.
- [ ] 실제 모델의 한국어 설명·근거 ID·데이터 버전·미확인 사항, 접근·토큰·도구 횟수 상한.
- [ ] Agent 실패가 핵심 업무를 막지 않는지 확인.
- [ ] Bojagi의 확인된 공식 SDK로 독립 테스트 후 분배 업무에 통합. 자산·단위·키·수신자 접근과 노출 범위를 명시.

**Bojagi 접근 조사는 1단계부터 병행한다.** 위 순서는 업무 통합의 순서이며 외부 의존성 확인을 마지막까지 미루는 계획이 아니다. 접근이 해소되지 않으면 GIWA·Dojang 기반 데모를 진행할 수 있으나 세 기술을 모두 실제 연동했다는 완료 조건은 충족하지 못한다.

### 6. 공개 배포와 전체 리허설

- [ ] SDK/native 의존성 호환성에 따라 EC2 ARM/x86_64 확정, 이미지 빌드·앱 전체 Compose 기동.
- [ ] EC2·EBS·비공개 S3·instance role·제한된 관리 접속·TLS reverse proxy 구성.
- [ ] Vercel 웹, Core 주소·허용 Origin·Secure 쿠키·비밀 설정, 내부 Agent·DB 포트 보호.
- [ ] 시작·중지·재시작, DB 보존·1회 백업/복원, 새 demo run의 샘플 리셋, 종료 자원 목록.
- [ ] 동시 5~10명·CSV 1천 행과 실제 시연 브라우저/지갑 조합으로 H01~H12 확인.
- [ ] 거래 제출 지연·RPC 오류·Agent 실패·Bojagi 연결 수준이 화면과 발표에서 사실대로 구분되는지 확인.

기존 v0.2의 해커톤 범위와 제외 항목을 유지한다. 행사 날짜가 정해지지 않아 달력 납기를 임의로 산정하지 않는다.

## 현재 실행 상태와 검증 근거

- 저장된 최근 Java 결과는 **20건 통과**다. 이번 점검에서 테스트를 재실행한 결과는 아니다.
- Next production build·브라우저·HTTP SIWE·GIWA 조회 결과는 [직전 개발 결과](wallet-status.md), [HTTP 증거](evidence/siwe-smoke.json)에 있다.
- 이번 점검에서는 로컬 3000·8080·8000 포트가 연결 거부였으며 Docker 엔진도 실행 중이 아니었다. 직전의 '실행 중' 기록은 해당 검증 시점의 상태다. 로컬/배포 리허설 전 개발 환경 재기동이 필요하다.
- AWS/Vercel 계정 전체를 조회한 것은 아니다. 현재 저장소에는 해당 앱의 클라우드 배포 결과·설정·주소가 없고 기존 개발 기록도 미배포 상태다.
